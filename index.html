01 / WHY SHOULD WE CARE?

私たちの日常は、
どれほど見えないインフラに依存しているのか？

動画を見る。地図を開く。ネットで買い物をする。写真を保存する。その多くは、遠く離れた場所にある巨大なコンピューター（データセンター）と、海や地面の下を通る光ファイバーで通信することで成り立っています。私たちが「クラウド」と呼ぶものは、空の上ではなく、地上に実在する物理設備です。

WHEN IT STOPS
サービスが止まる

決済、動画、SNS。裏側の建物や海底ケーブルにトラブルが起きると、普段使っているアプリも急に動かなくなります。

WHERE IT RUNS
世界に分散する

企業は世界中の都市に設備を分散して置き、利用者に近い場所から素早くデータを届けたり、地震などの災害に備えたりしています。

WHO CONTROLS IT
巨大基盤が支える

私たちが使う多くのWebサイトやアプリは、AWSやGoogle Cloud、Cloudflareといった巨大な共通インフラの上で動いています。

OBSERVATION BOUNDARY / HONESTY IN VISUALIZATION

何を表示し、何を表示しないか（できてるところ・できてないところ）

見えないインフラを可視化する際、最も避けるべきなのは「わからないことを、わかったように見せること」です。この観測端末では、実データとして取得できている事実と、概念モデル・非公開領域の境界を明確に区別しています。

● OBSERVABLE / できていること（実データ・公開仕様）
  • 公開Status APIのリアルタイム取得：Cloudflare および Google Cloud が公開しているJSONエンドポイントから現在の稼働状態・直近インシデントを直接取得しています。
  • リージョン都市の可視化：公式公開されているクラウド拠点都市（12拠点）と主要バックボーンの接続関係を表示しています。
  • 障害構造のモデル化：公開ポストモーテム（障害報告書）に基づく原因分類と、依存関係シミュレーションを実装しています。
○ NOT OBSERVABLE / できていないこと・あえて表示しないこと
  • データセンターの正確な建物位置：物理セキュリティ上非公開のため、番地レベルではなく都市座標として表現しています。
  • 実際の通信パケットのリアルタイム追跡：通信経路はミリ秒単位で動的に変わるため、03・04の図は概念モデル（Conceptual）として描いています。
  • 非公開API・海底ケーブルのライブ損傷検知：ブラウザから直接取得できない事業者APIや海底の物理センサーは推測で正常表示せず、「未取得・観測対象外」としています。
BUILD LOG / 001
DOCUMENTATION & NEXT STEP

何を考えて作ったか（制作の思考プロセスと設計判断）

「クラウド」という言葉は、あたかも空の上にデータが浮かんでいるような錯覚を与えます。しかし実際には、窓のない巨大なデータセンター、大量の冷却水と電力、そして海の底を這う光ファイバーという極めて物理的で壊れやすいインフラの上で私たちの日常は動いています。

制作にあたっては完成品の見栄えだけでなく、専門外の鑑賞者が「自分ごと」として構造を掴めることを重視しました。「一番近くの窓口拠点」「住所案内所」といった平易な表現への置き換えや、自分の手で基盤を止めて影響を確かめるシミュレーターはそのために設計しています。また、リアルタイムで取得できる公開APIと、概念モデルとして描いている部分を明確に分け、「わからないことをわかったように見せない」UI設計を貫きました。

DURATION & STACK
所要時間：約4.0時間（構成設計・UI実装・SVG回線アニメーション・公開API接続検証）
使用技術：HTML5 / Vanilla CSS / Vanilla JavaScript / SVG / Google Cloud & Cloudflare Public Status JSON API
WHAT WORKED / WHAT REMAINS
単一HTMLで完結する軽量設計によりGitHub Pages上で高速に動作。一方で、他社クラウドのリアルタイム統合や実際の応答速度（レイテンシ）実測は今後の課題として残している。
